# 자동 조립 리그 — 구현 기록

기준: `TFD_Auto_Assembly_League_Spec_v1.0.md` (2026-09-06).
이 문서는 그 기획서를 코드에 옮기면서 **결정한 것과 알려진 한계**만 적는다.
기획서 §15가 "코드에 이미 규칙이 있으면 그것을 우선"하라고 했으므로, 아래가 그 대조표다.

## 1. §15 대조 — 기존 규칙이 이긴 것

| 항목 | 기획서 임시안 | 코드에 있던 규칙 | 채택 |
|---|---|---|---|
| 역할 슬롯 | W2/D2/S3 | `pool_frame` = Core + W1 + D1 + flex ×3, 선체 100 | **기존** |
| 중복 획득 | 서로 다른 보상 간 허용 | uid 인스턴스 기반, 이미 허용 | **기존** |
| 증강 분리 | 분리 불가 | `Inventory.place`가 자동으로 뗀다 — **분리 가능** | **기존** |
| 숙주당 증강 슬롯 | 1개 | 1개 | 일치 |
| 전투 간 영구 성장 | 파츠별 명시 | `grow`는 전투 한정, 영구 성장이 없다 | 해당 없음 |
| 특수 팩션·희귀도 | 별도 풀 제외 | 90종이 전부 3팩션. Core는 이미 Salvage 제외 | 팩션 내부 균등 |
| 초반 보호 | 기본 OFF | 없음 | OFF |

`pool_frame`은 flexible이 3칸이라 **역할 슬롯 제약이 약한 골격**이다. 역할 제약 자체를
실험 축으로 보고 싶으면 별도 Frame이 필요하다 — 첫 결과 이후의 별도 실험이다 (§15 마지막).

## 2. 결정이 필요했던 셋

### 2.1 리그 공통 Core = 효과 없는 중립 Core

기존 Core 3종은 **팩션별이고 재질도 갈린다**(plating/biomass/plating). 조건마다 다른
Core를 쓰면 AI 4종 비교에 교란이 섞이므로 `league/data/league_core.json`에 효과 없는
Core를 하나 두었다.

- **본편 카탈로그에 넣지 않는다.** `sim/content.gd`의 `PART_PATHS`에 넣으면 파츠 수가
  오염되고 Salvage 후보로 샌다. `league/league_content.gd`만 이 파일을 덧붙여 읽는다.
- 팩션은 `first`다. 3팩션 중 하나를 쓰면 그 팩션 파츠의 `source_faction` 조건이 조용히
  참이 된다. `first`는 리그 풀에 등장하지 않으므로 부작용이 없다.
- **알려진 편향**: 재질 plating은 caustic을 1.5배, thermal을 0.75배로 받는다.
  Viridia에게 유리하고 Reclaimer에게 불리한 방향이며, 리포트 머리에 그대로 찍는다.
  재질 축은 별도 배치로 분리한다.
- **대가**: Core 효과(자재 5 / 영구 재생 / 보호막 50)가 리그에서 통째로 빠진다.
  여기서 찾은 후보를 프리셋으로 쓰려면 Core를 나중에 붙여야 한다.

### 2.2 예비 보관 6개

기존 코드에 한도가 없었지만 그것은 결정이 아니라 미구현이다 — 런은 Salvage가 5회뿐이라
한 번도 문제가 되지 않았다. 리그는 최대 17회 획득하므로 한도가 없으면 폐기 판단이
사라지고 엔진 투자형이 무한히 쟁여둘 수 있다. 기획서 기본안 6을 쓴다.

한도는 `Inventory`가 아니라 리그가 강제한다. 컨테이너는 규칙을 몰라야 한다.

### 2.3 이번 범위 = 단계 A~C

단계 D(800명 실행 + 후보 15~30개 추출 + 고정 상대군 재평가)는 다음이다.

## 3. 전투 로직을 새로 쓰지 않는 방법

기획서 §1.3: "새로운 전투 규칙이나 파츠 효과를 리그 안에서 임의로 구현하지 않는다."

그래서 초과 피해와 시간 초과 무승부는 **`combat_sim.rules`로 주입하는 선택 규칙**이고
구현은 `sim/combat_sim.gd` 안에 있다. 규칙을 넣지 않으면 기존 동작 그대로다.
`league/combat_adapter.gd`에는 전투 로직이 한 줄도 없다.

초과 피해의 성질 (§9.2):

- `take_typed_damage`를 지나지 않는 **유일한** 피해 경로다. 지나면 상성 배율과 보호막이
  걸리고 "양쪽에 같은 절대량"이라는 전제가 깨진다.
- 파츠 트리거를 발동시키지 않는다. 이벤트는 로그에 남기되 대기 큐를 비운다 —
  발동시키면 방어형 빌드가 초과 피해로 자기 엔진을 돌리는 역전이 생긴다.
- 소수 피해를 천분율 정수로 누적한다. 버리면 61초의 0.1이 매번 사라져 표와 어긋난다.
  테스트가 70초 5.5% · 80초 21%를 기획서 표와 대조한다.

## 4. AI 메타데이터는 자동 추출한다

기획서 §6은 파츠마다 메타데이터를 요구한다. **손으로 쓰지 않는다** — 이유는
`debug/part_text.gd`와 같다: 파츠를 고칠 때 두 곳을 고쳐야 하고 반드시 어긋난다.
90종에 손으로 붙이면 그 어긋남이 그대로 AI의 판단 근거가 된다.

`league/part_meta.gd`가 `on_fire`·`triggers` 블록에서 뽑는다. 대가는 **op이 늘 때마다
`OP_EFFECTS` 표에 한 줄을 추가해야 한다**는 것이고, `uncovered_ops`가 그걸 노출하며
테스트가 `Actions.OPS` 전수를 확인한다.

연결 판정의 규칙 하나: **같은 태그를 가졌다는 이유로 연결이라고 부르지 않는다** (§6).
연결은 "A가 만드는 이벤트를 B가 듣는다"이고, **방향까지 맞아야 한다** — 이벤트 키를
`이벤트@방향`으로 두어 적함에 나는 과열 틱을 자함 스코프로 듣는 가짜 연결이 애초에
만들어지지 않게 했다.

## 5. 실행이 드러낸 버그 넷

전부 리포트를 읽고 나서 잡았다. 코드 리뷰로는 하나도 안 보였다.

1. **조립 불가를 0점으로 표현했다.** 초반 점수는 흔히 음수다(빈 본체 자리·공격 불능
   페널티). 실패 신호가 0이면 정상 후보를 이겨서, 조립할 수 있는 파츠를 두고
   "아무것도 안 함"을 골랐다 — 시작 조립 실패의 진짜 원인이었다. `-INF`로 분리했다.
2. **후보 생성이 Core를 창고로 뺄 수 있었다.** 첫 실행이 전 매치 조립 실패로 끝났다.
   Core는 AI의 결정 공간이 아니라 배치의 비교 조건이다.
3. **제약을 아직 못 채운 중간 상태를 탐색에서 버렸다.** 첫 선택에서 본체 3개를 요구하게
   되어 모든 후보가 탈락했다. "펼칠 수 있는 상태"와 "고를 수 있는 상태"를 분리했다.
4. **§5.1의 본체 기회비용을 빠뜨렸다.** 증강이 순수 이득으로 보여 AI가 본체 자리를
   비워둔 채 전부 증강으로 돌렸다. 빈 본체 자리를 과잉 페널티에 넣었다.

## 6. 알려진 한계

- **탐색 비용이 크다.** 참가자 1명이 17회 선택하고, 선택마다 제안 3개 × 깊이 2 탐색을
  돈다. 40명에 57초, 200명에 수 분이다. 800명은 별도 시간이 필요하다.
- **트리거 발동 빈도는 명목값이다.** `build_graph`는 전투를 부르지 않으므로 (§5.2)
  트리거형 파츠의 기여를 4초 주기로 가정한다. 실제 빈도는 숙주에 따라 다르다.
- **AI 4종의 차이가 아직 작다.** 가중치는 기획서의 출발 제안이고 검증된 밸런스가 아니다.
  선택 로그(`choices.jsonl`)에 요소별 점수가 다 남으므로 조정 근거는 확보돼 있다.
- **적 프리셋은 아직 만들지 않았다.** 계열 분류와 고정 상대군 재평가는 단계 D다.
