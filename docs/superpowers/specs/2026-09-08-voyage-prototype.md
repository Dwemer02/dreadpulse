## 0. 무엇을 만들었나

A~G는 사람이 만져 볼 빌드와 비교 기준을 확보했다. 다음 불확실성은 AI 배치를 더
늘리는 것이 아니라 **보상과 전투를 사람이 읽고 판단할 수 있는지**에 있다 (§1).

그래서 K=5 수동 보상 선택과 8전투 시험 항해, 그리고 그 앞단인 조립 실험실을 만들었다.
답해야 할 질문은 셋이다 (§1).

1. 받은 파츠를 보고 지금 강화할 방법과 다음 연결을 준비할 방법을 모두 떠올릴 수 있는가?
2. 다음 적을 보고 메인 엔진을 유지하면서 보조 파츠·증강을 바꿀 이유가 생기는가?
3. 전투를 보고 왜 이겼는지, 무엇이 작동하지 않았는지 설명할 수 있는가?

**클리어율을 정하는 단계가 아니다.** 판단과 가독성의 문제를 찾는 단계다.

## 1. 실행 방법

| 무엇 | 어떻게 |
|---|---|
| 시험 항해 · 조립 실험실 | Godot 에디터에서 `res://debug/voyage_view.tscn`을 열고 **F6** |
| 화면 없이 같은 게임 점검 | `godot --headless --path . --script res://tests/run_voyage_check.gd -- --seeds=1,2,3` |
| 명부 강도까지 재기 (느리다) | 위 명령에 `--bench=1` |
| 첫 전투 상대 검수 | `godot --headless --path . --script res://tests/check_starter_enemies.gd` |
| 씬이 실제로 열리는지 | `godot --headless --path . --script res://tests/check_scenes.gd` |
| 단위 검증 | `bash tests/run.sh` (`tests/unit/test_voyage.gd` 포함) |

메인 씬(F5)은 **바꾸지 않았다** — 기존 미니 런 화면(`debug/run_view.tscn`)이 그대로
메인이다. 시험 항해는 리그 규칙으로 도는 별도 실험 장치이므로 F6으로 연다.

## 2. 계층 — `voyage/`는 어디에 있나

```
sim/ (전투 1판)
  ← run/ (런 1회) · league/ (AI 배치) · voyage/ (사람 1항해)
      ← debug/ · tests/
```

`voyage/`는 `sim/` · `run/inventory.gd` · `league/`를 읽는다. **`league/`와 `run/`은
`voyage/`를 모른다.** 소비자는 `debug/`와 `tests/`뿐이다.

`league/` 안에 넣지 않은 이유: 그쪽은 "AI 배치를 돌려 파츠를 밸런싱하는" 계층이고,
사람 플레이는 그 배치의 일부가 아니다. 섞으면 `league_runner`가 사람 입력을 알게 되고
배치 결과에 사람 모드가 새어 든다.

**리그 규칙을 다시 구현하지 않는다.** 초과 피해·시간 상한·중립 배율·보관 한도·손실
상한은 `voyage_config.league`(= `LeagueConfig`)가 그대로 들고 있다. 전투는
`combat_adapter.fight()`, 제안은 `offer_generator.offer_for()`, 조립 상태 변경은
`candidate_generator.apply()`, 합법성은 `build_loader.assemble()`이다 — 전부 AI가
쓰는 것과 같은 함수다.

| 파일 | 책임 |
|---|---|
| `voyage/voyage_config.gd` | 사람 플레이 프로필. 리그 설정을 감싸고 K·전투 수·경로만 덮어쓴다 |
| `voyage/voyage_state.gd` | 항해 상태 기계. **AI가 고르던 자리에 사람 입력이 들어온다** |
| `voyage/board_commands.gd` | 조립 명령과 조회. 검증은 AI와 공유하고 사람용 조회만 더한다 |
| `voyage/enemy_roster.gd` | 적 명부 로더 (`voyage/data/enemies.json`) |
| `voyage/enemy_brief.gd` | 적 보드 → 위협·대응 문장. **실제 파츠 정의에서 읽는다** |
| `voyage/combat_readout.gd` | 전투 결과 정리. 작동하지 않은 파츠에 **이유**를 붙인다 |
| `voyage/lab.gd` | 조립 실험실 (H1). 항해 상태 기계를 거치지 않는다 |
| `voyage/voyage_save.gd` | 저장·이어하기·내보내기 |
| `debug/voyage_view.gd` | 화면. **규칙을 하나도 갖지 않는다** |

## 3. 확정한 기본값 (§10.3의 표)

| 항목 | 이 구현이 쓴 값 | 근거 |
|---|---|---|
| 보상 수 | **K=5** (개발용으로 3·6 유지) | 3→5는 크고 일관된 개선, 5→6은 두 규모가 다섯 배 차이 (§3.1) |
| 형식 | 조립 실험실 → 8전투 항해 | §7.1·§7.2 |
| 시작 | 무작위 1개 + K=5 선택 2회, 3본체 | §7.2 |
| 획득 | **획득 10회 중 선택 9회** (완주 시) | 무작위 지급과 선택을 섞어 세지 않는다 (§11) |
| 실패 | 손실 4회 (무승부도 1) | 리그 규칙 재사용 |
| 상한 | 8전투 완주. **같은 전투에서 4번째 손실이면 탈락 우선** | §7.2 |
| 전투 규칙 | 60초 유예·61초부터 초과 피해·120초 종료·중립 배율 | 리그 규칙 재사용 |
| 보상 풀 | 첫 기본값 `equal` (R34/V33/A33), 시작 설정에서 기존 풀 선택 | §10.3 |
| 보관 | 6개. **넘치면 사람이 버릴 것을 고른다** — 자동 폐기 없음 | §7.3 |
| 초기 증강 | 시작 조립에서는 금지, 첫 전투 이후 허용 | §7.2 |
| 적 정보 | 보상 선택 전에 **다음 적의 전체 보드 공개** | §7.2 |
| 경로 | 시드로 정해진 고정 경로. 플레이어 빌드를 보고 바꾸지 않는다 | §7.2 |
| 무공격 출격 | **경고 후 허용** (사람용 프로필 한정) | §7.3 마지막 |

**무공격 출격은 사람 프로필에만 있다.** 자동 리그의 시작 생성 조건
(`require_operational`)은 바꾸지 않았다 — 그쪽은 공격 불능을 실험 조건 오류로 본다.

## 4. 적 명부 — 난이도표가 아니다

`voyage/data/enemies.json`에 13명이 있다. 둘은 손으로 짰고 열하나는 단계 G 프리셋의
보드를 **새 id로** 가져왔다 (`source`에 원본 id가 남아 있다, §6.4).

**원본 라운드는 획득 예산을 짐작하는 단서이지 배치할 스테이지 번호가 아니다** (§6.1).
그래서 경로를 데이터로 두었고, 플레이해 보고 고치는 것을 전제로 한다.

### 4.1 첫 경로 (`first_path`)

| 전투 | 적 | archive-1 승률 | 왜 여기 |
|---:|---|---:|---|
| 1 | `ve_starter_gun` | 55.6% | 손으로 짠 3본체. 순수 피해만 — "내 피해가 통한다"만 확인 |
| 2 | `ve_scrap_lash` | 65.7% | 단순 공격 + 회복 하나. 읽기 쉬운 첫 G 후보 |
| 3 | `ve_heat_salvager` | 58.3% | 자원 회수 연결을 보여 준다 |
| 4 | `ve_regen_answer` | 66.7% | 회복에 반응하는 연결 |
| 5 | `ve_growth_coil` | 68.5% | 회복→성장 연결. 장기전 여부 확인 |
| 6 | `ve_swift_lance` | 82.4% | 빠른 공격형 |
| 7 | `ve_late_frame` | 79.6% | 항해 후반 — 실제 획득 예산과 대응 가능성 |
| 8 | `ve_late_pressure` | 94.4% | **검수 대상** — R8에서 포화하지 않은 둘 중 하나지만 높다 |

승률은 전부 고정 상대군 archive-1에서 잰 것이고 **사람 난이도가 아니다.**

### 4.2 첫 전투 상대를 다시 짰다

첫 판본(`scrap_autocannon` 2정 + `recast_barrel`)은 archive-1에서 **74.1%**였다 —
2~3전투에 놓을 G 초반 후보(58~73%)보다 **셌다.** 첫 전투가 3전투보다 어려우면
곡선이 뒤집힌다. `tests/check_starter_enemies.gd`로 후보 여덟 개를 재고
`scrap_autocannon + recast_barrel + erosion_extruder`(55.6%)로 바꿨다.

두 번째 손짜기 적(`ve_starter_ward`, 45.4%)은 **경로에 넣지 않았다.** 평균 63초에
108판 중 17판이 초과 피해 없이는 끝나지 않는다 — "회복을 앞지르는 출력"을 가르치는
상대지만 첫 경로에 놓으면 사람이 120초를 기다리게 된다. 실험실과 대안으로 둔다.

### 4.3 위협 설명은 정의에서 읽는다

§6.2가 못 박은 것이다: **버킷 문자열을 그대로 노출하지 않고**, 아직 구현을 확인하지
않은 공략을 약속하지 않는다. 그래서 `enemy_brief.gd`는 손으로 쓴 문장을 데이터로
굳히지 않고 파츠 정의에서 읽는다 — 쿨타임, 피해 타입, 상태이상, 회복·보호막이 전부
정의에 있다. 파츠 수치를 고치면 설명이 함께 바뀐다.

대응 문장은 전부 `sim`의 실제 동작에서 확인했다.

| 상태이상 | 확인한 동작 |
|---|---|
| 과열 | 1초마다 **남은 중첩만큼** Thermal 피해, 보호막이 흡수하고 중첩이 하나 줄어든다 |
| 부식 | 파츠마다 쌓이고 **그 파츠가 발동할 때** 쌓인 만큼 Caustic 피해가 들어온다 |
| 파열 | 함선에 누적되고 선체 이하로 떨어지면 붕괴한다 — 회복이 붕괴선을 밀어낸다 |
| 정지 | 그 파츠의 **발동만** 막는다. 트리거는 계속 돈다 |

## 5. 결과 화면이 말해야 하는 것

§7.1의 마지막 항목이 요구한 넷을 `combat_readout.gd`가 만든다.

- **주요 피해·방어·회복** — 낸 피해를 경로별로, 회복·보호막·과열 흡수·받은 선체 피해
- **실제 트리거 연결** — 정적 어휘가 아니라 이 전투에서 실제로 이어진 것
- **초과 피해 개입** — "마지막 타격이었다" / "깎기 시작한 뒤 일반 종료" / "깎기 전에
  종료" / "120초 상한"을 구별한다
- **작동하지 않은 파츠의 확인 가능한 이유**

마지막이 이 구현에서 가장 많이 손본 부분이다. 기여를 다섯으로 가른다.

| 유형 | 뜻 | 화면 문장의 예 |
|---|---|---|
| `fired` | 발동했다 | 발동 12회 · 출력 12회 |
| `reacted` | 발동은 없었지만 실제 출력을 냈다 | 트리거로 4회 출력했다 |
| `waiting` | 주기 발동이 없는 파츠가 조건을 못 만났다 | `overheat_applied`를 기다렸다 |
| `silent` | 주기 발동이 있는데 아무것도 안 했다 | 막혔다 — 자재 부족(3회 진입) |
| `inert` | 구조적으로 불가능하다 | 효과가 없는 시험용 Core다 — **판정 제외** |

**이유를 못 찾으면 못 찾았다고 적는다.** "발동도 출력도 없었고 막힌 기록도 없다 —
이유를 확인하지 못했다"가 실제 문장이다. 추측을 적지 않는다.

회복 파츠가 발동했는데 출력이 0인 경우는 따로 적는다 — `sim`은 **실제로 선체가
올라간 경우만** `repaired`를 방출하므로 "만피에서 수리했다"가 출력 0으로 보인다.
그것을 "출력 없음"으로만 적으면 고장으로 읽힌다.

## 6. 저장·기록

저장은 **경계에서** 한다: 보상 생성 · 선택 확정 · 조립 완료 · 전투 결과 확정.

재개하면 같은 제안·상대·시드를 유지하고 **보상이 두 번 지급되지 않는다.** 제안은
(풀, 시드, 획득 index)만으로 결정되므로 다시 뽑아도 같은 목록이고, 이미 받은 index는
`_taken_index`가 막는다. 저장 파일에 제안 목록을 넣어 두고 그것을 믿지 않는 이유는
제안 생성 규칙이 바뀌었을 때 저장이 조용히 옛 규칙으로 계속 돌기 때문이다.

내보내기(`user://voyage/export/<시각>/`)는 셋을 쓴다.

- `history.jsonl` — 제안 전체·선택한 개체와 사용 방식·조립 전후·전투 결과·메모
- `state.json` — 재현에 필요한 상태 (버전·시드·경로·보드·창고)
- `summary.txt` — 사람이 읽는 한 줄 요약들

기록은 자동 수집이 기본이다 (§9). 매 선택마다 설문을 띄우지 않고, 창고 파츠에
"이 선택 기록" 버튼(메모)만 둔다 — "지금은 약하지만 다음 연결을 기다린다" 같은
이유를 남기고 실제 사용 순간까지 추적할 수 있다.

## 7. 검증 — 무엇을 확인했나 (§8.3)

`tests/unit/test_voyage.gd` 86 checks + `tests/check_scenes.gd` + `tests/run_voyage_check.gd`.

| §8.3의 항목 | 어디서 |
|---|---|
| 같은 보드·시드의 헤드리스 결과가 같다 | `_test_same_seed_same_combat` — 승패·시간·이벤트 수 |
| 배속·일시정지가 결과를 바꾸지 않는다 | 전투가 **이미 끝난 뒤** 로그를 재생한다 (구조로 보장) |
| 불법 역할·증강 중복·개체 복제가 막힌다 | `_test_illegal_commands_are_blocked` |
| 저장 후 재개해도 제안·상대·개체가 그대로 | `_test_save_resume_keeps_everything` |
| 4번째 손실·마지막 전투·시간 초과의 경계 | `_test_loss_limit_beats_combat_cap` |
| 엔진 오류를 게임상 패배로 기록하지 않는다 | `voyage_state.launch()`의 `combat_error` 경로 |
| 실제 시작 화면에서 조립→전투→보상→종료→내보내기 | `tests/check_scenes.gd`의 `_drive_voyage()` |

**단위 테스트는 씬을 로드하지 않는다.** 그래서 `check_scenes.gd`를 따로 두었다 —
이전에 리포터의 문법 오류를 배치가 잡지 못한 것과 같은 구멍이 화면에도 있다.

검증이 실제로 잡은 결함 넷:

1. **메모가 재개 후 사라졌다.** JSON을 지나면 Dictionary의 int 키가 String이 되어
   `notes[uid]`가 영원히 비어 보였다.
2. **불법 역할 장착이 통과했다.** `candidate_generator.apply()`의 place는 실패하지
   않는다 — 인벤토리 컨테이너는 슬롯 역할을 모른다. AI는 후보 생성에서 걸러지지만
   사람은 아무 슬롯이나 지목할 수 있다.
3. **효과 없는 Core가 연쇄의 뿌리로 세어졌다.** 화면 문장에 "league_core → flex_2"가
   찍혔다 — 우리 보드에 없는 슬롯까지.
4. **첫 전투 상대가 3전투 상대보다 셌다** (§이 문서 4.2).

## 8. 아직 하지 않은 것

- **§4.1의 레시피 항 비교 실험** — 검토 문서가 "첫 플레이 구현의 선행 조건이 아니다"라고
  명시했다. 고정형 AI는 현재 비교군을 그대로 둔다.
- **파츠 수치·AI 가중치 조정** — A~G 내내 손대지 않았고 여기서도 안 했다.
- **상대군 갱신** — `archive-1`은 회귀 기준으로 보존한다. 사람용 난이도 기준을 새
  버전으로 추가하는 것은 첫 플레이 이후다 (§6.1).
- **§5의 투자 로그 확장** — 회수 시점·남은 기회·미회수 사유를 나누는 기록은 자동
  배치 쪽 항목이라 이번에 넣지 않았다. 사람 플레이는 메모로 대신한다.
- **여러 함선·지도·진화·보너스 목표** — 첫 플레이 이후다 (§1의 표).
- 메인 씬 교체, 독립 실행 파일, 웹 이식 (§10.3 마지막).

## 9. 첫 플레이에서 볼 것 (§9)

디자이너 본인의 3~5런으로 시작한다. **승률 추정이 아니다.**

| 반복되는 현상 | 우선 수정 |
|---|---|
| 5장 중 쓸 이유가 있는 것이 계속 없다 | 선택 로그의 풀·역할·기능적 대체재 확인 → K=6 비교 |
| 잘못 이해해서 좋은 파츠를 버린다 | 본체/증강·숙주·비용·조건 설명과 미리보기 |
| 다음 적이 달라도 늘 같은 강화만 한다 | 적 위협의 차이와 소규모 대응의 이득 확인 |
| 적마다 전체 보드를 갈아야 한다 | 적의 요구 완화 또는 대응 파츠의 범용성 |
| 준비한 파츠가 끝까지 창고에만 있다 | 남은 기회·공급·실제 대체 선택 검토 |
| 대부분의 승부를 초과 피해가 정한다 | 초반 적·시작 공격 경로·지속력부터 확인 |
| 같은 엔진이 새 시드에서도 손쉽게 반복된다 | 풀별 재현·전환 비용 확인 후 공급 구조 조정 |

같은 시드를 반복하면 학습 효과가 생기므로 **반복 연습과 새 시드의 결과를 구분한다.**
본인 몇 런의 승률로 고정형/유연형 우열을 확정하지 않는다.
